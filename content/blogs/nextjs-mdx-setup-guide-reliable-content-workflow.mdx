My first MDX setup was fragile. A small config change would break parsing, a typo in frontmatter would surface as a runtime crash, and I never quite trusted that a post would render until I opened it in the browser.

The problem wasn't MDX. It was treating content as an afterthought instead of as data. This is the setup that fixed it, and it's what runs this blog.

## The idea: content is data with a schema

The flow has three parts:

1. **`content/`** holds MDX files. That's the source of truth.
2. **[Velite](https://velite.js.org)** reads them, validates the frontmatter against a schema, compiles the MDX, and writes typed output to `.velite/`.
3. **Pages import that output** like any other module, with full types.

If a post has a bad date or a missing title, the build fails with a clear message. Nothing broken reaches production.

## The Velite config

```ts
// velite.config.ts
import { defineConfig, defineCollection, s } from "velite";

const posts = defineCollection({
  name: "Post",
  pattern: "blogs/*.mdx",
  schema: s
    .object({
      slug: s.path(),
      title: s.string().max(99),
      description: s.string().max(999).optional(),
      date: s.isodate(),
      published: s.boolean().default(true),
      tags: s.array(s.string()).optional(),
      body: s.mdx(),
    })
    .transform((data) => ({
      ...data,
      slugAsParams: data.slug.split("/").slice(1).join("/"),
    })),
});

export default defineConfig({
  root: "content",
  output: {
    data: ".velite",
    assets: "public/static",
    base: "/static/",
    name: "[name]-[hash:6].[ext]",
    clean: true,
  },
  collections: { posts },
});
```

A few things doing real work here:

- `s.path()` derives the slug from the file path, so there's no slug to keep in sync by hand.
- `s.isodate()` rejects dates that aren't valid, which catches the classic `2024-13-01` typo.
- `published` defaults to `true`, and setting it to `false` keeps drafts out of the build.
- `s.mdx()` compiles the body at build time, so the page only has to run the compiled code.

## Wiring it into Next.js

Add a path alias so the generated output imports cleanly:

```json
// tsconfig.json
{
  "compilerOptions": {
    "paths": {
      "#site/content": ["./.velite"]
    }
  }
}
```

Then run Velite before Next in both scripts:

```json
// package.json
{
  "scripts": {
    "dev": "concurrently \"velite dev --silent\" \"next dev --turbopack\"",
    "build": "velite build --clean && next build --turbopack"
  }
}
```

In dev, Velite watches `content/` and rebuilds as you write. In CI, make sure you run the full `build` script, not just `next build`. Otherwise `.velite` won't exist and the import will fail.

Add `.velite` to `.gitignore`. It's generated output.

## Rendering MDX

Since Velite already compiled the MDX to a function body, rendering is short:

```tsx
// components/mdx-components.tsx
import * as runtime from "react/jsx-runtime";
import Image from "next/image";

const components = { Image };

function useMDXComponent(code: string) {
  const fn = new Function(code);
  return fn({ ...runtime }).default;
}

export function MDXContent({ code }: { code: string }) {
  const Component = useMDXComponent(code);
  return <Component components={components} />;
}
```

Anything in `components` can be used inside posts, so custom callouts or demos are one import away.

## Static pages from typed data

The post page looks up the slug and pre-renders every post at build time:

```tsx
// app/blogs/[...slug]/page.tsx
import { posts } from "#site/content";
import { MDXContent } from "@/components/mdx-components";
import { notFound } from "next/navigation";

export function generateStaticParams() {
  return posts.map((post) => ({ slug: post.slugAsParams.split("/") }));
}

export default async function PostPage({
  params,
}: {
  params: Promise<{ slug: string[] }>;
}) {
  const { slug } = await params;
  const post = posts.find((p) => p.slugAsParams === slug.join("/"));

  if (!post || !post.published) notFound();

  return (
    <article>
      <h1>{post.title}</h1>
      <MDXContent code={post.body} />
    </article>
  );
}
```

`post.title`, `post.date` and `post.tags` are all typed from the schema. Rename a field in the config and TypeScript shows you every place that needs updating.

The same typed `posts` array drives the blog index, the sitemap and the article's structured data, so there's one source for all of them.

## Why "boring" is the goal

With this in place, writing a post is just writing. Create a file, fill in four lines of frontmatter, and the build either accepts it or tells you exactly what's wrong. That predictability is what keeps a blog alive. The less you fight the tooling, the more you write.
