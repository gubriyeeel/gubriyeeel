"Move fast" and "keep the codebase clean" sound like they pull in opposite directions. In my experience they mostly don't. What slows teams down isn't the time spent writing good code. It's the time spent rewriting, debugging, and being afraid to touch code that nobody fully understands.

These are the habits that have actually made me faster, across startups and larger product teams.

## 1. Validate data at the edges, trust it inside

A lot of frontend bugs come from data that isn't the shape you thought it was: a field that's sometimes `null`, a number that arrives as a string, an array that's missing on old records.

The fix is to check the shape once, where the data enters your app, and then trust the types everywhere else:

```ts
import { z } from "zod";

const Job = z.object({
  id: z.string(),
  title: z.string(),
  salary: z.number().nullable(),
  tags: z.array(z.string()).default([]),
});

export type Job = z.infer<typeof Job>;

export async function getJob(id: string): Promise<Job> {
  const res = await fetch(`/api/jobs/${id}`);
  return Job.parse(await res.json());
}
```

Now components don't need defensive `?.` chains everywhere, and when the API changes you get one clear error at the boundary instead of a broken UI three screens away.

## 2. Build the real flow first, styles last

I start with the plainest version that does the whole job end to end: real data, real mutations, real error handling, ugly UI.

This surfaces the hard questions early. What happens when the request fails? What does the empty list look like? Is the data even available? Those answers change the design. Polished components built before that point often get thrown away.

## 3. Ship small, behind a flag

Big pull requests are slow to review, risky to merge, and painful to roll back. I'd rather merge five small ones behind a feature flag:

- The data layer and types.
- The basic UI, hidden.
- Error and empty states.
- The polish.
- Removing the flag.

Each piece is easy to review and safe to deploy. The feature reaches production early, where real data can show you what you missed.

## 4. Copy twice, abstract on the third time

Early abstractions are guesses about how code will change. Usually they guess wrong, and then every new use case adds another prop or flag to a component that was supposed to be simple.

My rule: duplicating code once is fine. When I need the same thing a third time, I've seen enough real variations to know what the abstraction should actually be.

## 5. Make features easy to delete

Most features get changed or removed eventually. The easiest code to maintain is code you can take out cleanly.

In practice that means:

- Keep a feature's components, hooks and types in one folder.
- Avoid reaching into other features' internals.
- Name things after what they do, so you can search for everything related.

If deleting a feature means deleting a folder and one route, you're in good shape. If it means hunting through shared utils for special cases, that's the debt to pay down.

## Name the debt you take on

Sometimes cutting a corner is the right call. When you do, write it down where the next person will see it:

```ts
// TODO(gab, JOB-412): Copy is hardcoded in English. Move to i18n before we add a second language.
```

An owner and a ticket turn a vague worry into a task. Unnamed shortcuts are the ones that turn into "nobody touch that file."

## The real definition of fast

Speed isn't how quickly you type. It's how rarely you have to go back. Clear boundaries, small changes and deletable features keep the second number low, and that's what compounds.
